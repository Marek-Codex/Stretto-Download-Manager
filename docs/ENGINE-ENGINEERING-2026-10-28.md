# Transfer engine precision pass — October 28, 2026

The target is useful throughput with bounded resource use. More requests are
worth keeping when they improve the transfer, not just because the settings allow
them. No client can predict every server's limits or guarantee the fastest result.

## What changed

- Strong ETags pin each range with If-Match. Last-Modified provides a conditional
  fallback when available. Conflicting response validators fail before that body
  is written. Weak ETags no longer authorize a byte-exact saved resume.
- Permanent failure cancels sibling requests and observes their completion before
  surfacing the original error. Added connections cannot hide a changed entity as
  an ordinary optional connection refusal.
- A marginal throughput result gets one confirmation window. A substantial
  regression or explicit refusal still backs off immediately; zero throughput
  does not trigger speculative expansion.
- The controller stops probing near an explicit speed ceiling. An unknown
  bottleneck still uses measured throughput. An unlimited limiter remains unlimited.
- Startup respects the host's learned connection ceiling, including fixed mode.
  Existing shared-host cooldowns, range validation, work stealing and retry policy
  remain in use.

This uses the existing asynchronous worker/controller design. No service, new
runtime dependency, per-connection thread or persistent profiling database was added.
Host limits are reactive and cannot guarantee that a server will never throttle
or reject a request. With no trustworthy remote validator, changes cannot always
be detected; Last-Modified also has coarser precision than a strong ETag.

## Controlled benchmark

One local run used a deterministic generated 16 MiB file, a 500,000-byte/sec
per-connection server cap, and a 16-connection adaptive ceiling:

| Mode | Elapsed | Average reported throughput |
|---|---:|---:|
| Single connection | 35.63 s | 459.9 KiB/s |
| Adaptive, ceiling 16 | 7.17 s | 2.2 MiB/s |

Elapsed-time ratio: 4.97×. Sampled live progress reached six active connections.
Both outputs passed a complete check of the generated byte pattern and matched
SHA-256. The old harness summary counted allocated ranges as "connections";
that label now reports the configured ceiling and the separately measured peak.

Reproduce with two terminals, using an unused local port:

```powershell
node tools/testserver.js --port 18111 --size 16777216 --throttle 500000
dotnet run --project Stretto.Check -c Release -- http://127.0.0.1:18111/engine-benchmark.bin --benchmark --adaptive -n 16 -o artifacts/engine-benchmark
node tools/verify.js artifacts/engine-benchmark/bench-1/engine-benchmark.bin 16777216
node tools/verify.js artifacts/engine-benchmark/bench-16/engine-benchmark.bin 16777216
```

Run benchmarks separately from the regression suite; its fixtures use their own
local ports. This is one synthetic scenario, not a comparison with another product,
an old-versus-new adaptive result, an internet-speed guarantee, or a CPU/RAM study.
Multi-connection gains disappear when another shared bottleneck sets the limit.

## Build identity

Installer payloads include ENGINE-BUILD.json with the SHA-256 of Stretto.Core.dll,
its assembly version, source commit/status and a hash of the Core C#/project files.
The DLL hash identifies the shipped engine bytes. The source hash covers those
files, not every SDK, compiler, build setting or external dependency.

This is a public build identity, not an unremovable ownership watermark. Its
contents are covered by the containing signed package; an unsigned manifest can
be replaced along with a modified DLL. Third-party media tools remain separate
components, not claims of Stretto engine authorship.

## Verification

The full isolated run passed all 56 engine tests. The Release solution build
passed with zero warnings/errors, and all four extension regression scripts passed.

Engine regressions cover capped connections, shared host limits, refusals,
plateaus, interruption/resume, content integrity and permanent failure. New checks
cover compliant and noncompliant changed-entity responses, weak tags, a file
changing on an added connection, cancellation of sibling header waits, marginal
measurement confirmation, zero-progress restraint and explicit speed ceilings.

The build-manifest helper was checked against the actual assembly hash, correctly
reports modified Core sources and emits no absolute workspace paths.
